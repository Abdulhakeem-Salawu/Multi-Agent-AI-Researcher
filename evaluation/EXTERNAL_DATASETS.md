# External benchmark integrations

This integration adds reusable loaders and deterministic scoring helpers for three public datasets. They remain separate from the internal, human-adjudicated ResearchBench schema because their annotation types and scoring meanings are not interchangeable.

## Tracks and label provenance

| Dataset | Track | Label type | What it measures |
|---|---|---|---|
| DeepResearch Bench II (DRB II) | Report rubrics | Expert-refined, atomic report rubrics; a judge returns 1, 0 or -1 | Information recall, analysis and presentation in generated research reports |
| FRAMES | Multi-hop QA | Dataset-provided answer and relevant Wikipedia article URLs | Multi-hop reasoning, answer correctness and retrieval |
| BrowseComp-Plus | Fixed-corpus retrieval and research | Human-verified evidence-document and gold-document labels | Finding evidence and answer-bearing documents in a fixed corpus |

Do not describe all three as human-annotated in the same sense. DRB II uses expert-authored reports and rubrics that were manually revised and expert-reviewed, but its per-run rubric scores are produced by an LLM judge. FRAMES provides gold answers and article references; its dataset card does not specify annotator-level adjudication. BrowseComp-Plus explicitly describes its evidence and gold document references as human-verified retrieval labels. None supplies our internal four-way claim-verification labels with evidence spans.

## Registry and adapters

The machine-readable registry is evaluation/external/registry.json. It records upstream locations, track purpose, annotation provenance, licence scope and corpus restrictions.

Python adapters are in evaluation/external/adapters.py:

- load_deepresearch_bench_ii_jsonl(path) reads the official tasks_and_rubrics.jsonl, keeps the task-level licence, rubric dimensions, blocked-source metadata and upstream IDs. CC BY 4.0 and CC0 are included by default. The two CC BY-NC 4.0 tasks are excluded by default; only set include_noncommercial=True for a non-commercial use after checking current rights.
- load_frames_tsv(path) reads the official test.tsv and preserves the upstream row index, question, answer, reasoning types and relevant article URLs. It does not fetch or store Wikipedia article bodies.
- load_browsecomp_plus_jsonl(path) consumes the de-obfuscated JSONL generated by the official upstream script. It retains query IDs, answer labels, evidence/gold/negative document IDs and URLs, but intentionally discards document text.

Each item uses ExternalBenchmarkItem, a thin wrapper that preserves labels in the dataset-specific annotations object. These items are not BenchmarkCase instances and cannot be passed to the internal ResearchBench scorer.

## Download the source files locally

External data belongs under data/external/, which is ignored by Git.

### DeepResearch Bench II

~~~bash
mkdir -p data/external/drb2
curl -L \
  https://raw.githubusercontent.com/imlrz/DeepResearch-Bench-II/main/tasks_and_rubrics.jsonl \
  -o data/external/drb2/tasks_and_rubrics.jsonl

research-external inspect deepresearch-bench-ii \
  --input data/external/drb2/tasks_and_rubrics.jsonl
~~~

The upstream repository states that the licence follows each source article. Its current task file includes 129 CC BY 4.0 tasks, two CC BY-NC 4.0 tasks (idx 26 and 110), and one CC0 task (idx 119). The adapter requires an explicit per-task licence and excludes non-commercial tasks by default. Preserve attribution and the exact source-file SHA-256 in each experiment record. Do not assume the upstream code licence overrides the per-task data licences.

### FRAMES

~~~bash
mkdir -p data/external/frames
curl -L \
  https://huggingface.co/datasets/google/frames-benchmark/resolve/main/test.tsv \
  -o data/external/frames/test.tsv

research-external inspect frames --input data/external/frames/test.tsv
~~~

The Hugging Face dataset card identifies FRAMES as Apache-2.0 and documents 824 multi-hop questions with gold answers and relevant Wikipedia links. This adapter stores the references only, not the linked Wikipedia content. Pin the dataset revision and record the input file SHA-256 before comparing model versions.

### BrowseComp-Plus

BrowseComp-Plus publishes an obfuscated query/evidence dataset and a separate fixed corpus. Use the official project repository and its scripts_build_index/decrypt_dataset.py workflow to prepare the local JSONL; do not implement an alternative decoder or publish a decrypted copy.

~~~bash
git clone https://github.com/texttron/BrowseComp-Plus.git external/BrowseComp-Plus
python -m pip install datasets
python external/BrowseComp-Plus/scripts_build_index/decrypt_dataset.py \
  --output data/external/browsecomp_plus_decrypted.jsonl

research-external inspect browsecomp-plus \
  --input data/external/browsecomp_plus_decrypted.jsonl
~~~

The preparation command checks that the cloned code repository is checked out at the pinned decoder commit before executing it. The upstream workflow may require Hugging Face authentication. Read its current instructions and terms before downloading. The query/evidence file contains 830 queries; the separate corpus contains about 100,195 documents. The adapter does not load that corpus and does not retain the full document text embedded in evidence records. The HF card has an MIT label, but crawled webpage content can remain subject to source-specific rights. Do not mirror or commit the corpus or decrypted benchmark files into this public repository. Use only an approved local or controlled evaluation environment, and check corpus rights before redistribution.

## Scoring helpers

evaluation/external/scoring.py provides:

- score_drb2_rubric_judgments(item, judgments): requires one score for every rubric ID and reports counts/rates for satisfied (1), not mentioned (0) and blocked-reference (-1) outcomes, overall and by dimension. It intentionally does not collapse the three categories into a single average.
- score_frames_answer(prediction, reference): normalized exact match and token F1. These are answer-level string metrics; they do not replace expert review of multi-hop reasoning.
- score_frames_retrieval(item, retrieved_article_urls, k=10): retrieval metrics against dataset-provided relevant article URLs.
- score_browsecomp_plus_retrieval(item, retrieved_docids, k=10): separate metrics against evidence and gold document IDs. Do not merge the two judgement sets; gold docs are a stricter subset with a distinct meaning.

These deterministic helpers score existing predictions/rankings only. They do not call an LLM, download data, infer labels, or set quality thresholds.

## Reproducibility and release rules

Before producing a scored comparison, record:

1. Dataset ID, official upstream URL, exact upstream commit/revision and split.
2. SHA-256 of each downloaded input file.
3. Adapter version (the Git commit containing this integration).
4. Licence scope and any per-task filtering.
5. Model, model version, prompt versions, retrieval configuration and scoring parameters.

The upstream DRB II project also reported in August 2026 that tasks 112 and 114 were temporarily excluded from its leaderboard scoring pending expert review and repair. This adapter preserves the full 132-record source file; reproducing a particular upstream leaderboard requires matching its exact task inclusion rules and evaluator version.

The registry points to upstream main branches for discovery; it is not itself a frozen benchmark release. Pin immutable revisions before publishing a comparison. Do not commit downloaded datasets, decrypted BrowseComp-Plus queries, web document bodies, or retrieval indexes to this repository. These external tracks complement, but do not replace, the internal frozen snapshot and human adjudication workflow.

## Reproducible ingestion, fixed-corpus retrieval and actual agent runs

Install the optional Hugging Face dataset reader:

~~~bash
pip install -e ".[benchmark]"
~~~

Download the pinned DRB II or FRAMES text inputs. The downloader verifies the parsed record count and writes a SHA-256 sidecar manifest:

~~~bash
research-external download deepresearch-bench-ii --output-dir data/external
research-external download frames --output-dir data/external
research-external inspect frames --input data/external/frames/test.tsv
research-external inspect deepresearch-bench-ii --input data/external/drb2/tasks_and_rubrics.jsonl
~~~

The downloader includes all 132 DRB II source tasks in the local input. The runner excludes its two CC BY-NC tasks unless explicitly requested with --include-noncommercial. Confirm that your use complies with the current task-level licences before using any such item.

BrowseComp-Plus query records are large and obfuscated. Clone the official code at its pinned revision, then prepare a lightweight local query file using the upstream decoder. The output deliberately excludes every document body:

~~~bash
git clone https://github.com/texttron/BrowseComp-Plus.git external/BrowseComp-Plus
cd external/BrowseComp-Plus
git checkout 046949032b0328319cc9a02663a759ec601d9402
cd ../..

research-external prepare-browsecomp-plus \
  --upstream-repo external/BrowseComp-Plus \
  --output data/external/browsecomp-plus/queries.jsonl \
  --revision 144cff8e35b5eaef7e526346aa60774a9deb941f
~~~

For a small decoder smoke test, add --limit 10. The default prepares all 830 queries. This does not download the 100,195-document corpus.

### Fixed-corpus BrowseComp-Plus index

The separate corpus is approximately 1.76 GB compressed upstream. Indexing all documents can require several gigabytes of local disk. The command streams the pinned corpus into a local SQLite FTS5 index; document text remains in that local index and must not be committed or redistributed.

~~~bash
# Smoke test: first 500 documents only; not an official benchmark score
research-external build-browsecomp-index \
  --revision 89e412cede7d9904f0e8b717aebd9b317c46dfdc \
  --output data/external/browsecomp-plus/corpus-smoke.sqlite3 \
  --limit 500

# Complete corpus index for full retrieval evaluation
research-external build-browsecomp-index \
  --revision 89e412cede7d9904f0e8b717aebd9b317c46dfdc \
  --output data/external/browsecomp-plus/corpus.sqlite3
~~~

The BrowseComp-Plus run path requires the complete corpus index. It returns upstream document IDs with each retrieved passage so evidence and gold retrieval metrics can be computed against the original judgments. A 500-document index is only a plumbing smoke test and must not be presented as the benchmark result.

### Run the actual agent

The run command invokes the same LangGraph graph used by the application, writes each task result to predictions.jsonl, and saves a run_manifest.json containing input SHA-256, selected task IDs, Git commit, model ID/revision, search provider and corpus revision. It also writes summary.json with track-specific aggregate metrics. Failed tasks are recorded individually. --resume skips already completed task IDs, retries failed tasks, and refuses to append when the dataset inputs, task selection, model, corpus revision or corpus index checksum differs from the original run.

For the Modal cloud workflow, the default model is Qwen/Qwen3-1.7B, loaded directly from Hugging Face with Transformers on an NVIDIA L4. The requested Hub ref (default: main) is resolved through the Hub API to an immutable commit SHA before tokenizer and model weights are loaded; that SHA is written to the run manifest. The Modal workflow also accepts a model_revision input so a previous run can be repeated against the exact same snapshot. The same loaded model handles agent generation and evaluator/extractor calls; outputs are labelled same_model_llm_judge. See the Modal cloud section below for model cache and evaluation limitations. Local or custom OpenAI-compatible runs can still use LLM_BASE_URL and EVAL_JUDGE_LLM_BASE_URL.

FRAMES uses the judge model only to extract a concise answer from the generated report; exact match and token F1 are then computed deterministically against its answer label. DRB II uses an LLM judge with exact report-substring evidence checks and native 1/0/-1 rubric outcomes. BrowseComp-Plus uses a separate LLM answer judgment and deterministic evidence/gold retrieval metrics. Judge outputs are not human labels.

The runner records the agent base URL, model identifier, query/retrieval limits, retrieval mode and judge endpoint/model as well as data checksums. The endpoint values should be non-secret base URLs; do not put API keys or bearer tokens in URLs. It flushes telemetry after task execution. The runner preserves the first run's timestamp and records subsequent code revisions in the run manifest's resume_history. Aggregates count the latest result per task, so a failed task that is successfully retried is not double-counted. Raw predictions remain append-only for auditability.

Example runs:

~~~bash
# FRAMES smoke run; it is not a fixed-corpus reproduction.
research-external run frames \
  --input data/external/frames/test.tsv \
  --output-dir evaluation/runs/frames-smoke \
  --limit 5

research-external run deepresearch-bench-ii \
  --input data/external/drb2/tasks_and_rubrics.jsonl \
  --output-dir evaluation/runs/drb2-smoke \
  --language en \
  --limit 2

research-external run browsecomp-plus \
  --input data/external/browsecomp-plus/queries.jsonl \
  --corpus-index data/external/browsecomp-plus/corpus.sqlite3 \
  --output-dir evaluation/runs/browsecomp-plus-smoke \
  --limit 5
~~~

The --language en or --language zh option filters DRB II before applying --offset and --limit. Leave it unset to use the mixed-language source set. The filter is intended for DRB II; FRAMES and BrowseComp-Plus do not expose this language field through this runner. The first smoke run should be small: each task may invoke several search queries, LLM completions and (for DRB II) multiple rubric-judge batches. Do not compare smoke-run metrics to published benchmark scores. Run a full split only after inspecting costs, failure rates, selected language/domain and the recorded run manifest. The live-web tracks are not fixed-corpus reproductions; only BrowseComp-Plus uses its pinned corpus index.


## Run benchmark downloads and experiments on Modal (recommended)

The optional Modal runner executes dataset preparation, corpus indexing and model-scored experiments in Modal cloud containers. GitHub Actions only checks out this repository, installs the runner dependencies and starts the Modal job. It does **not** download DRB II, FRAMES or the BrowseComp-Plus dataset/corpus. Modal workers fetch the upstream data directly and persist it in a Modal Volume.

This keeps multi-gigabyte transfers away from a phone tethered to your laptop. The repository source and small control messages still pass through GitHub Actions and Modal, but the benchmark files and full corpus remain inside Modal. Do not run `modal volume get` for the corpus or data directory on a metered local connection.

### One-time GitHub Actions secrets

Your existing `TAVILY_KEY` secret is supported directly. You do not need to rename it.

Required repository secrets:

| Secret | Purpose |
|---|---|
| `MODAL_TOKEN_ID` | Modal CI authentication token ID |
| `MODAL_TOKEN_SECRET` | Modal CI authentication token secret |
| `TAVILY_KEY` | Your existing Tavily credential for live-web research |

Optional secrets:

| Secret | Purpose |
|---|---|
| `HF_TOKEN` | Hugging Face access token; not needed for the public Qwen3-1.7B model |
| `LANGFUSE_BASE_URL`, `LANGFUSE_PUBLIC_KEY`, `LANGFUSE_SECRET_KEY` | Existing Langfuse observability credentials |

Optional repository variables include `MODAL_ENVIRONMENT`, `LANGFUSE_TRACE_CONTENT` and `OTEL_EXPORTER_OTLP_ENDPOINT`.

The benchmark workflow has a configurable `model_id` input, defaulting to **`Qwen/Qwen3-1.7B`**. You can select another Hugging Face repository ID later without editing the agent code.

### How Qwen3 inference is hosted

Hugging Face currently does not list Qwen3-1.7B as deployed by its serverless Inference Providers. Instead, this project loads the public Hugging Face weights directly in a Modal GPU function using Transformers. The initial runtime is an **NVIDIA L4 GPU**.

- Agent generation and evaluator/extractor calls share one in-memory model instance to avoid loading two copies.
- Qwen3 thinking mode is disabled for the initial baseline; generation uses the non-thinking chat template and the Qwen3 recommended sampling settings.
- The resolved Hugging Face commit revision is stored in the experiment manifest.
- Weights are cached under the persistent Modal Volume `multi-agent-ai-research-qwen-cache`, separate from the dataset and benchmark-results Volume. After the first download, later jobs can reuse this cache.
- `HF_TOKEN` is optional for this public model, but can be added later if a selected model requires gated access.

**Evaluation caveat:** The same Qwen3 model is used to generate the research report and judge/extract its answer. Its scores are labelled `same_model_llm_judge` and are not independent verification. These are useful baseline diagnostics, not human evaluation and not an unbiased quality estimate. For a stronger evaluation later, we can retain Qwen3 as the agent and introduce a separate, stronger evaluator model.

Modal GPU execution consumes compute while the model is loaded and running; persistent volumes also have storage costs under your Modal plan. The L4 model worker is started only for the benchmark run, not kept as an always-on inference service.

Modal's local setup does not automatically authenticate GitHub Actions. The workflow uses `MODAL_TOKEN_ID` and `MODAL_TOKEN_SECRET`. Create a separate CI token with `modal token new` and store both values as repository secrets. Do not paste them into source files.

### First run: small FRAMES preparation

Open **GitHub → Actions → Remote external benchmark → Run workflow**.

Choose:

| Input | Value |
|---|---|
| Dataset | `frames` |
| Model ID | `Qwen/Qwen3-1.7B` |
| Stage | `prepare` |
| Limit | `3` (ignored during preparation) |
| Offset | `0` |

This reuses the already-prepared 824-row FRAMES file in the Modal Volume.

Next, run the same workflow with `dataset_id=frames`, `model_id=Qwen/Qwen3-1.7B`, `stage=run` and `limit=3`. This starts the L4 GPU worker, downloads Qwen3 weights into the persistent model cache if needed, then runs three questions through the research agent and same-model evaluator. It requires `TAVILY_KEY`, but no external `LLM_BASE_URL` or judge endpoint secrets.

### BrowseComp-Plus: split preparation from corpus indexing

Do not begin with `stage=all` for your first run. Use three separate workflow dispatches:

1. `dataset_id=browsecomp-plus`, `stage=prepare`: downloads/decrypts the 830 query records on Modal and stores only question, answer, document IDs and URLs in the persistent Volume.
2. `dataset_id=browsecomp-plus`, `stage=build-corpus`: streams the pinned 100,195-document corpus directly from Hugging Face into a local SQLite FTS5 index on the Modal Volume. This is the large download/indexing step and may require several GB of persistent storage.
3. `dataset_id=browsecomp-plus`, `stage=run`, `limit=3`: runs the selected task slice against the complete fixed-corpus index.

The application enforces the full 100,195-document corpus and expected upstream revision before it will score BrowseComp-Plus. The local index and experiment outputs are kept in Modal storage, not checked into GitHub.

### Retrieve only a small summary (optional)

Each run prints its aggregate `summary.json` in the GitHub Actions log. Detailed outputs remain on the persistent Modal Volume named `multi-agent-ai-research-benchmarks`.

To list stored run folders:

~~~bash
modal volume ls multi-agent-ai-research-benchmarks runs
~~~

To retrieve just a small summary file, not the corpus or input datasets:

~~~bash
modal volume get multi-agent-ai-research-benchmarks \
  runs/frames/YOUR_RUN_TAG/summary.json ./frames-summary.json
~~~

The default run tag is the GitHub workflow run ID and attempt (for example `123456789-1`). The run tag and paths are printed in the workflow log. Avoid retrieving `data/external` or the BrowseComp-Plus `corpus.sqlite3` unless you deliberately want a multi-gigabyte transfer.

### Storage and cost behaviour

Modal Volumes are persistent: data written by one run can be reused by later runs, and the runner explicitly commits its downloads, index and outputs. This avoids downloading the corpus again on every run. Modal compute time and persistent storage are still subject to your Modal workspace's current pricing and account limits. Remove the Volume only when you deliberately want to delete the cached datasets and every stored run:

~~~bash
modal volume delete multi-agent-ai-research-benchmarks
~~~

The workflow serializes runs to avoid concurrent writers updating the same persistent Volume. For a cloud run, Modal's Volume must be in the same Modal environment selected by the workflow (your workspace default unless `MODAL_ENVIRONMENT` is set).
